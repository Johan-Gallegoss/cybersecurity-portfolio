Proyecto 01: Descubriendo Mi Red

Auditoría y diagnóstico de conectividad de red en un sistema Kali Linux virtualizado bajo esquema NAT. Este informe técnico documenta de forma completa la identificación de interfaces IP, la puerta de enlace predeterminada, la resolución DNS del sistema, las pruebas de integridad ICMP y el comportamiento del trazado de rutas externas.

Ver Procedimiento y Evidencias Siguiente: Lab 02 (Wireshark) →

Objetivos y Alcance del Laboratorio

El propósito de este laboratorio es analizar metódicamente la configuración de red y el comportamiento de la pila TCP/IP en un entorno Linux, comprendiendo cómo se comunican las interfaces locales con la red interna y hacia hosts externos en Internet:

  • ✓ Identificación de direccionamiento IP: Reconocer las interfaces activas, direcciones IPv4/IPv6 asignadas y máscaras de subred bajo direccionamiento privado RFC 1918.
  • ✓ Determinación de la puerta de enlace (Gateway): Identificar el salto inicial configurado para enrutar el tráfico fuera del segmento de red virtual.
  • ✓ Auditoría de resolución DNS: Comprobar los servidores de nombres configurados a nivel de sistema operativo para la traducción de nombres de dominio.
  • ✓ Diagnóstico de conectividad bidireccional: Evaluar la transmisión y recepción de paquetes hacia destinos en Internet mediante el protocolo ICMP.
  • ✓ Análisis de saltos y enrutamiento: Rastrear el camino recorrido por los paquetes capa a capa y documentar el comportamiento de las respuestas en entornos NAT virtualizados.

Entorno de Ejecución y Parámetros Auditados

Las pruebas se ejecutaron sobre una máquina virtual con el sistema operativo Kali Linux configurada bajo el modo de red NAT (Network Address Translation) en el hipervisor VirtualBox. Los valores concretos comprobados en las evidencias son:

Dirección IP Local

10.0.2.15/24

Interfaz eth0 (MTU 1500)
Puerta de Enlace

10.0.2.2

Gateway NAT VirtualBox
Segmento de Red

10.0.2.0/24

Broadcast: 10.0.2.255
Servidor DNS IPv4

192.168.100.1

Vía NetworkManager / Host

Procedimiento Técnico, Comandos y Resultados

A continuación se presenta el desglose de cada una de las 5 actividades realizadas en el laboratorio, con el comando exacto ejecutado, la salida de la terminal y su análisis técnico correspondiente:

PASO 01

Identificación de Interfaces y Dirección IP

Se utilizó el comando ip a (abreviatura de ip address show) para listar todas las interfaces de red configuradas en el kernel de Linux.

El prefijo OUI de la dirección MAC (08:00:27) identifica la tarjeta de red como una interfaz virtual emulada por Oracle VirtualBox, lo que confirma el entorno de laboratorio. La interfaz eth0 aparece en estado UP con direccionamiento dinámico DHCP dentro del segmento privado RFC 1918.

🔍 Ampliar captura

Evidencia — Salida de ip a

Interfaces lo y eth0 activas. IP 10.0.2.15/24, MAC 08:00:27:8a:35:d2 (OUI Oracle VirtualBox).

PASO 02

Identificación de la Puerta de Enlace (Gateway)

Se ejecutó ip route para inspeccionar la tabla de enrutamiento del kernel e identificar la ruta por defecto empleada para comunicaciones hacia el exterior.

La dirección 10.0.2.2 no es un router físico; es el componente de NAT interno de VirtualBox que traduce el tráfico de la máquina virtual hacia la interfaz de red real del equipo anfitrión. Esta es la única ruta de salida configurada.

🔍 Ampliar captura

Evidencia — Salida de ip route

Ruta por defecto default via 10.0.2.2 dev eth0 proto dhcp src 10.0.2.15 metric 100. El gateway NAT de VirtualBox está operativo.

PASO 03

Auditoría de Servidores DNS

Se consultó el archivo del sistema /etc/resolv.conf para identificar los servidores resolutores de nombres configurados.

El archivo es gestionado por NetworkManager y se sobreescribe automáticamente. El servidor DNS indicado (192.168.100.1) no pertenece al segmento virtual 10.0.2.0/24; corresponde al gateway físico de la red del host, cuya dirección propaga VirtualBox a la VM a través del mecanismo NAT.

🔍 Ampliar captura

Evidencia — Contenido de /etc/resolv.conf

Archivo generado por NetworkManager. DNS primario nameserver 192.168.100.1 (IPv4) y nameserver fd17:625c:f037:2::3 (IPv6).

PASO 04

Verificación de Conectividad e Integridad con ICMP

Se ejecutó ping google.com -c 4 para comprobar la conectividad de extremo a extremo enviando exactamente 4 solicitudes ICMP Echo Request.

La prueba confirma conectividad bidireccional completa: el sistema pudo resolver el nombre, enrutar los paquetes a través del NAT y recibir las respuestas ICMP Echo Reply sin pérdida. El valor TTL recibido (64) indica que los paquetes no fueron manipulados por un proxy transparente en el camino.

🔍 Ampliar captura

Evidencia — Salida de ping -c 4 google.com

Conectividad ICMP bidireccional confirmada: 0% de pérdida de paquetes hacia Internet.

PASO 05

Análisis de Ruta de Red y Saltos

Se ejecutó traceroute google.com para observar los saltos intermedios (hops) que recorren los paquetes hasta el destino.

Por qué los saltos muestran * * *: traceroute en Linux envía sondas UDP hacia puertos altos (33434+) con TTL incremental. El motor NAT de VirtualBox y los firewalls intermedios descartan esas sondas o bloquean los mensajes ICMP Time-to-Live Exceeded (Tipo 11, Código 0) de retorno. Los asteriscos indican ausencia de respuesta a las sondas, no falta de conectividad: la prueba con ping del paso anterior ya confirmó que el enlace hacia Google es completamente funcional.

🔍 Ampliar captura

Evidencia — Salida de traceroute google.com

Salto 1: 10.0.2.2 responde (~1.2 ms). Saltos 2–24: * * * por filtrado de sondas UDP/ICMP en el motor NAT de VirtualBox.

Conclusiones, Limitaciones y Aplicabilidad

Conclusiones del Laboratorio

Se comprobaron experimentalmente los pilares fundamentales del networking en Linux: la asignación dinámica de parámetros mediante DHCP en un segmento privado RFC 1918 (10.0.2.0/24), el papel del Gateway virtual (10.0.2.2) como intermediario hacia redes externas, la resolución de nombres DNS y la comprobación de conectividad sin pérdida mediante ICMP.

Limitaciones de las Pruebas Realizadas

  • • Aislamiento NAT no equivale a seguridad perimetral total: La máquina virtual accede a Internet a través de la IP del host y no es directamente accesible desde la red local externa sin reenvío de puertos (Port Forwarding), pero esto constituye una propiedad de la arquitectura NAT, no una política de seguridad o cortafuegos auditada.
  • • Pruebas en capa 3 y 4 básicas: No se analizaron protocolos de nivel superior ni reglas de inspección profunda de tráfico (lo cual se aborda en el Laboratorio 02 con Wireshark).
  • • Restricciones de traceroute en NAT: El comportamiento observado evidencia que las herramientas de diagnóstico basadas en sondas UDP pueden verse condicionadas por la emulación de red del hipervisor.

Aplicabilidad en Roles de Ciberseguridad

Para analistas en Centros de Operaciones de Seguridad (SOC) y roles de Blue Team, dominar estos diagnósticos desde la consola de comandos permite descartar rápidamente falsas alertas de caída de servicio, identificar direcciones de origen privadas frente a públicas en trazas de eventos, y validar la ruta de paquetes antes de iniciar tareas de captura o mitigación de incidentes.
