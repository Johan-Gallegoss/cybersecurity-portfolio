Proyecto 02: Análisis de Tráfico con Wireshark

Captura e inspección de paquetes de red en tiempo real desde un entorno Kali Linux virtualizado. Este laboratorio analiza el comportamiento real de tres protocolos fundamentales — ICMP, DNS y TCP/TLS — utilizando Wireshark como herramienta de captura y las utilidades de terminal ping, nslookup y curl para generar el tráfico.

Ver Análisis y Evidencias ← Anterior: Lab 01 (Red)

Objetivos y Alcance del Laboratorio

El objetivo de este laboratorio es observar y comprender cómo se comportan los protocolos de red en comunicaciones reales, analizando el flujo de paquetes desde la perspectiva de un capturador pasivo. Las actividades se enfocaron en tres protocolos:

  • ✓ICMP: Observar en Wireshark los mensajes Echo Request y Echo Reply generados por ping, verificando la correspondencia de secuencias y la conectividad bidireccional.
  • ✓DNS: Capturar las consultas de resolución de nombres enviadas por el sistema y las respuestas del servidor DNS, identificando los registros A (IPv4) y AAAA (IPv6) devueltos.
  • ✓TCP y TLS: Desglosar el establecimiento de una conexión TCP segura mediante el saludo de tres vías (SYN, SYN-ACK, ACK) y la negociación TLS, incluyendo el mensaje Client Hello con el indicador SNI.

Entorno de Ejecución y Herramientas

Las capturas se realizaron desde una máquina virtual con Kali Linux configurada en modo NAT bajo VirtualBox, utilizando la misma infraestructura del Laboratorio 01. La interfaz de captura fue eth0 (IP local 10.0.2.15).

Análisis de Tráfico por Protocolo

A continuación se presentan los tres bloques de análisis realizados, cada uno con su evidencia original de Wireshark.

ANÁLISIS 01

Tráfico ICMP — Echo Request y Echo Reply

Se ejecutó ping google.com -c 4 mientras Wireshark capturaba con el filtro de display icmp en la interfaz eth0. El objetivo era observar la estructura de los paquetes ICMP y confirmar la correlación entre petición y respuesta.

Wireshark reveló el intercambio completo: paquetes de tipo Echo Request desde 10.0.2.15 hacia 142.251.0.101 (servidor Google) y los correspondientes Echo Reply en sentido inverso. Cada par de paquetes comparte el mismo identificador (id=0xadac) y un número de secuencia incremental, lo que permite verificar que ninguna respuesta quede sin su solicitud. El TTL de 64 en los replies indica que el tráfico regresa sin ser modificado por un proxy intermedio. Los resultados del ping visibles en la terminal (0% packet loss) son consistentes con lo observado en la captura.

ANÁLISIS 02

Tráfico DNS — Resolución de Nombres

Se ejecutó nslookup openai.com mientras Wireshark capturaba con el filtro dns. El objetivo era observar el ciclo completo de consulta y respuesta DNS sobre UDP puerto 53.

La captura muestra cuatro paquetes: una consulta de tipo A (registro IPv4) seguida de su respuesta, y una consulta de tipo AAAA (registro IPv6) seguida de su respuesta. Ambas consultas parten de 10.0.2.15 hacia el servidor DNS 192.168.100.1 sobre UDP puerto 53. La respuesta a la consulta A devuelve las direcciones 104.18.33.45 y 172.64.154.211, confirmadas también en la salida de nslookup visible en la terminal. El hecho de que el sistema emita automáticamente dos consultas (A y AAAA) demuestra el comportamiento estándar del resolver moderno, que intenta resolución dual-stack IPv4/IPv6.

ANÁLISIS 03

TCP 3-Way Handshake y Negociación TLS

Se ejecutó curl https://example.com mientras Wireshark capturaba con el filtro tcp. El objetivo era observar el establecimiento de la conexión TCP y el inicio de la negociación de cifrado TLS.

La captura muestra la secuencia completa del saludo de tres vías: paquete SYN desde el puerto efímero local 48894 hacia el puerto 443, seguido del SYN-ACK del servidor y el ACK de confirmación que establece la sesión TCP. Inmediatamente después, Wireshark identifica un mensaje TLSv1.3 Client Hello con el campo SNI (Server Name Indication) establecido en example.com, lo que revela el dominio destino incluso cuando la carga útil posterior está cifrada. La comunicación utiliza IPv6 (fd17:625c:f037:2:6e… → 2606:4700:10::ac42…), consistente con la configuración dual-stack observada en el Lab 01.

Relevancia del campo SNI: Aunque TLS cifra el contenido del mensaje, el campo SNI del Client Hello viaja sin cifrar en la mayoría de implementaciones de TLS 1.3 sin ESNI/ECH. Esto permite a un analista de red — o a un firewall de inspección profunda — conocer el dominio de destino de una conexión HTTPS sin descifrar el tráfico, lo que es relevante tanto para el análisis defensivo como para la privacidad del usuario.

Conclusiones, Limitaciones y Aplicabilidad

Conclusiones del Laboratorio

El laboratorio demostró que es posible observar y correlacionar el comportamiento de tres protocolos de capas distintas en un entorno real. Los tres análisis produjeron resultados coherentes entre sí y con los datos del Laboratorio 01: la misma IP local, el mismo servidor DNS y el mismo gateway NAT aparecen en las capturas.

Limitaciones de las Pruebas Realizadas

  • •Alcance pasivo: Wireshark se usó únicamente como capturador pasivo; no se realizaron análisis de archivos .pcap almacenados ni capturas de larga duración.
  • •Entorno NAT limitado: El modo NAT de VirtualBox oculta parte del tráfico real del host anfitrión; la captura refleja únicamente el tráfico de la VM.
  • •TLS no descifrado: Los datos de aplicación TLS son visibles como bloques opacos (Application Data). El laboratorio no incluyó descifrado de sesiones TLS con claves exportadas.

Aplicabilidad en Roles de Ciberseguridad

El análisis de paquetes es una competencia fundamental para analistas SOC y Blue Team. Conocer la estructura de los protocolos permite identificar tráfico anómalo (escaneos ICMP, queries DNS a dominios sospechosos, handshakes TCP incompletos), detectar comunicaciones con servidores C2 y establecer líneas base de comportamiento de red. El campo SNI visible en TLS Client Hello es un ejemplo de cómo metadatos no cifrados permiten la inspección sin romper el cifrado.
